# LLM連携

## 方式

Gemini を利用者自身のAPIキーで直接呼びます。アプリが直接呼ぶときの既定は `gemini-3.6-flash`、
サーバー経由のときは `gemini-3.5-flash-lite`
で、設定画面から変更できます。
構造化出力（`responseMimeType: application/json` と `responseSchema`）で
`docs/AI_RESPONSE_CONTRACT.md` の形を要求し、返ってきたものを
`validateMayaResponse` で必ず検証してから画面へ渡します。

### アーキテクチャ方針との差

`docs/TECH_ARCHITECTURE.md` §9 は「プロバイダをクライアントから直接呼ばない」
と定めています。**現状はこれに従っていません。**

理由は、単独運用のアプリであること、利用者自身のキーを端末のキーチェーンに
置く方式（Voicebox で実績のある形）を採ったこと、バックエンドがまだ無いこと。
アプリにキーを同梱してはいないので「鍵をバンドルしない」原則は守っています。

**配布するなら変える必要があります。**他人に配る場合、キーを利用者から預かる
形は運用も責任も重くなるため、バックエンド経由へ移します。そのときに変わるのは
`src/services/llm/geminiClient.ts` の呼び出し先だけで、プロンプトも検証器も
そのまま使えます。

## キーは2つ

無料と有料を、**別々の Google Cloud プロジェクト**のキーとして登録します。
無料は Billing なしのプロジェクト、有料は Billing 有効のプロジェクトです。
1つのキーにフラグを立てる形では、どちらの枠に落ちるかを保証できません。

キーは `expo-secure-store` で端末のキーチェーンにのみ保存します。

### 無料枠と機密情報

無料枠のプロジェクトは、送信内容がサービス改善に使われる場合があります。

MAYA は会社プロフィールを**毎回の相談に注入する**設計なので、Voicebox のように
「録音ごとに利用者が判断する」形では守れません。実在する会社の数字や取引先の
名前を扱うときは、有料キーを登録してからにします。設定画面にもその旨を出して
います。

`settings.ts` の `freeTierAllowed` がこの判定の置き場所です。Phase 4 で会社
プロフィールが実データを持ったら、ここを通して無料枠を塞ぎます。

## 費用の歯止め

| 仕組み | 既定 |
| --- | --- |
| 無料優先 | ON |
| 上限時に有料へ切替 | **OFF** |
| 有料の1日上限 | 50円 |

切り替えるのは無料枠の 429 のときだけです。認証エラー、安全性による拒否、
壊れた応答、通信障害では切り替えません。同じ理由で2回失敗するだけで、それを
確かめるために金を払うのは筋が悪いためです。

上限は送信**前**に、1回の相談を保守的に見積もって加算し、超える見込みなら
止めます。Google の請求上限ではなく、こちら側のブレーカーです。

利用実績は SQLite の `llm_usage` に記録し、設定画面に当日分を出します。

## 実測で分かったこと（2026-09-11）

架空の会社（金属加工・28名・売上4〜5億円）で3往復を繰り返し検証しました。

### 使わないフィールドを要求してはいけない

最初、契約にある `summary` をスキーマに含めていました。2ターン目でモデルが
その中でループし、出力上限に達して **JSON が文字列の途中で切れました**。
画面には出ないフィールドのために、応答1回が壊れたわけです。

対処は3層にしました。

1. `summary` をリクエストスキーマから外した。描画していないので要求しない
2. `maxOutputTokens: 2048` を設定。暴走しても安く止まる
3. `finishReason: MAX_TOKENS` を検出し、「途中で切れました」と明示する。
   そうしないと JSON の解析失敗として出て、原因を探す場所を間違える

検証器にも全文字列フィールドの上限を入れてあります。防御は重ねます。

### responseSchema の maxLength は効かない

`decision.title` に `maxLength: 60` を指定しても、100字超が返ってきました。
**スキーマの長さ制限はモデル側で強制されません。**

### 短くしろと書くと、その指示について考え始める

プロンプトに良い例と悪い例を並べたところ、モデルが `title` の中で
「ルール確認：何を決めたかだけを言い切る。30字以内。」と書き始めました。
小さなフィールドの隣に指示を詰め込むと、指示そのものが出力に漏れます。

### 効いたのは required だった

`decision` の `required` を `['detected']` から
`['detected', 'title', 'reason']` に変えたら一度で直りました。

`reason` を必須にするまで、モデルは `reason` を一度も返さず、理由まで `title`
に詰め込んでいました。**書く場所を与えないと、隣の欄に書きます。**

結果は `title: 競合の10%値下げに追従せず価格を維持` / `reason: 粗利率が24.4%まで
低下し、同じ粗利額を稼ぐために必要な45%の増産が工場のキャパシティ上不可能なため。`

### 判断の誤検出はプロンプトで止まった

相談されただけの段階で `decision.detected: true` が返っていました。
「検討中」「方針を策定」は判断ではない、と明示して直りました。

これは Phase 5 に直結します。誤検出を許すと、決めていないことが記録に残ります。

### 会社情報は実際に効いている

注入した従業員数と売上レンジから1人あたり売上を計算し、「人手不足ではなく
稼働のムラ」と結論づけました。課題として書いた「見積作成に3日」も、次の一手の
根拠に使われています。

### annoyed は指定しないと出ない

「また同じ話で恐縮だけど」に対して `serious` が返っていました。
キャラクターバイブルの看板表情なので、前置きの言い回しを名指しして
`annoyed` を選ばせています。

### 禁止事項だけ書くと人格が消える

初版の人格定義は、5行の禁止事項と割合の数字だけでした。結果は正確ですが
つまらない、コンサルタントの所見のような応答になりました。

仕様書（PRD §5）は **warm / sometimes playful / capable of mild teasing** を
求めているのに、プロンプトにその言葉が1つも入っていませんでした。承認済みの
キャラクターシートにある口癖も使っていませんでした。

直したのは3点です。

1. **誰なのかから始める。**「Gakkyに一番近い相棒」「厳しいことを言うのは味方
   だから」を先頭に置き、禁止事項は最後に回した
2. **声を与える。**シートの口癖4つと、好きなもの・苦手なものを渡した。
   「Gakky、無理しすぎですよ？」のような言い回しが自然に出るようになった
3. **残りの2割を守らせる。**「8割が分析」と書くだけでは、残りが消えます。
   距離の近さが具体的にどう出るか（冒頭か末尾のひと言、Gakkyの状態に触れる、
   親しいから言える範囲でからかう）を例示した

あわせて、毎回同じ形で返すのをやめさせました。断定→根拠→選択肢3つ→次の一手を
繰り返すと読み物になり、会話でなくなります。`options` は道が本当に分かれている
ときだけ、短い返答でよい場面では短く、と明示しています。

変更後、「最近あんまり寝てなくてさ」に対して concerned で
「さっきから少し顔色悪かったですよ？Gakky、無理しすぎです」と返し、前の会話にも
触れるようになりました。朝の挨拶では coffee のポーズを選びます。

### 人格を足したら、作り話も増えた

人格を書き直した直後の実会話で、3つ出ました。どれも私の書き方が招いたものです。

**（訂正）会社名の捏造ではありませんでした。**「株式会社あさひの経営参謀」を
作り話だと判断しましたが、Gakkyが Company 画面に登録済みの内容でした。MAYA は
注入された文脈を正しく使っていただけです。転記だけを見て、登録の有無を確かめずに
決めつけたのはこちらの誤りです。

ただし、会社情報が**未登録のとき**にプロンプトからそのセクションごと消えるのは
実際の穴でした。「知らない」と書いていなければ、モデルは空白を埋めます。
いまは未登録の場合も「何も渡されていません。推測で補わないでください」と明示して
送ります。備えとしては正しいので、この変更は残します。

**見えないものを見たと言いました。**「今日はまた一段と疲れた顔してますよ」
「また夢中になってる顔してますね」。距離の近さの例として私が
「Gakkyの状態に触れる」と書き、それを視覚的な主張に広げられました。

MAYA にカメラはありません。PRD §6 は「事実と推測を分ける」ことを求めています。
姿を見たふりは、その原則に真っ向から反します。**言われたことには触れてよい、
文章から読み取ったことも言ってよい、見たことにしてはいけない**と分けました。

**同じ角度から刺し続けました。**7往復のうち4回が「脱線してますよ」系の指摘で、
小言になっていました。0.5割の挑発が3割くらいで動いていた計算です。
「一度言ったら次は別の入り方をする」「押すのは2割」と明示しました。

**直接の質問を飛ばして説教に入りました。**「普通のAI彼女アプリってどんなUI？」
に対して、答えずに「競合を真似しても強みは消えない」と返しました。反対するのと
答えないのは別です。まず答えてから続ける、と書き足しました。

修正後は、会社名を訊き返し、UIの定番構成を答えてから「ただし真似すると」と
続けるようになりました。

### 会話が終わらないと、時間が溶ける（2026-09-13）

アプリは起動するたびに最後の会話を開き直し、新しい会話を始めませんでした。
3日分が1つの会話になり、履歴は日付の無い文だけでモデルに届いていました。

MAYAには3日前の発言と5分前の発言の区別が付きません。前日の発言を「さっき」と
呼び、前夜の話題を翌朝の「おはようございます」にそのまま続けました。

同じ理由で、**書き出したログを読む側も誤りました。** 書き出しは会話の開始時刻を
1回出すだけだったので、既に直した失敗が再発に見えました。

直したのは3点です。

1. **会話をGakkyが区切れるようにした。** 新しい会話のボタンと一覧。判断は会社に
   紐づくので、どの会話からも同じ判断を覚えています
2. **時間が空いたところにだけ〔日時〕を付けて渡す。** 別の日、または3時間以上の
   間。全行に付けると時刻を読み上げる癖が付くので付けません
3. **書き出しに発言ごとの時刻と日付の見出しを出す**

### 道具と JSON の両立（2026-09-13 実測）

v0.2 で MAYA に道具を渡す前に、「道具を呼ばせる」と「決まった JSON で返させる」を
同じ問い合わせで使えるかを、無料キーと `gemini-3.6-flash` で確かめました。
スキーマは MAYA の実物、道具は架空の会社の売上を返す1つです。

| 質問 | 結果 | 時間 |
| --- | --- | --- |
| 先月の粗利率は？ | 道具を呼んだ | 8.5秒 |
| 同じ質問に道具の結果を返す | 必須欄のそろった JSON で答えた | 5.7秒 |
| おはよう | 道具を呼ばず、そのまま JSON で答えた | 3.8秒 |

**両立します。** 道具の宣言と `responseSchema` を同時に渡しても拒否されず、道具が
要らない質問では呼ばずに答えました。最終の返答は、指示したとおり取り込み時刻を
添えていました。

分かったことが3つあります。

- **モデルの発話はそのまま返す。** Gemini 3 は思考の署名を付けて返すので、道具の
  結果を渡すときに、モデルの発話を加工せず会話に戻しました。これで通っています
- **道具を使う質問は、使わない質問の3〜4倍かかる。** 往復が2回になり、道具を呼ぶか
  決める段階で思考に1,229トークン使っていました。「考えています…」の表示が長くなる
- **今日の日付を渡さないと、期間を取り違える。** 「先月」を 2024-05 と解釈し、返って
  きた 2026-08 の数字を疑わずに使いました。本番のプロンプトは現在時刻を渡していますが、
  道具の結果にも対象期間を入れ、サーバーで突き合わせます

1回目は `503`（混雑）で、待って取り直すと通りました。v0.2 のサーバーにも、混雑時に
間を空けて取り直す処理を入れます。

## モデルの選択（2026-09-11 実測）

**新しく作ったキーでは古いモデルが使えません。**`gemini-2.5-flash` は
`NOT_FOUND: no longer available to new users` を返し、Google 自身が 3.6 を
案内してきます。既存プロジェクトのキーでは通るため、手元のキーで試していると
気づけません。

新しい無料キーで `gemini-3.8-flash` を使うと、1分以上待たされた末に 503 が
返りました。最新のモデルは無料枠で混み合います。

架空の会社で3往復ずつ測った結果です。

| モデル | 1往復 | 中身 |
| --- | --- | --- |
| `gemini-3.6-flash` | 約9秒 | 「10%下げると同じ粗利額に45%の増産が要る」まで計算する |
| `gemini-3.5-flash-lite` | 約2秒 | 方向は正しいが数字の検算をしない。**サーバーの既定** |
| `gemini-3.8-flash` | 応答せず | 新しい無料キーで503 |

数字を出せることが MAYA の核なので、当初は速さより検算を取って 3.6 を既定にしました。

### 費用の規則の置き場所（2026-09-14）

サーバー経由のときの規則は **D1 が正**です。`server/wrangler.jsonc` の
`PREFER_FREE` / `ALLOW_PAID_FALLBACK` / `PAID_DAILY_LIMIT_YEN` は初期値で、
設定画面から変えたものが `server_settings` に入り、そちらが勝ちます。
上限を変えるのにデプロイし直す必要はありません。

表が無い状態（マイグレーション前）では初期値にそのまま落ちます。設定の読み取りで
相談を落とさないためです。

アプリの設定画面には歯止めのカードが2枚あります。**別物です。**

| カード | 効く経路 | 保存先 |
| --- | --- | --- |
| サーバーの費用の歯止め | サーバー経由 | サーバーの D1 |
| 費用の歯止め（直接呼びのとき） | アプリが直接 Gemini を呼ぶ | 端末のキーチェーン |

鍵の置き場所が違うので、規則も別々に持ちます。サーバー経由のとき、設定画面の
APIキー欄とモデル選択は使われません。

`ALLOW_PAID_FALLBACK` の初期値を `true` にしました（2026-09-14）。無料枠が
1日20回で止まるため、相談の途中で打ち切るより有料キーで続ける方がよい、という判断です。
切り替わるのは無料枠の上限に当たったときだけで、認証エラーや通信障害では切り替えません。

### 無料枠で 3.6 が使えなかった（2026-09-14）

**`gemini-3.6-flash` の無料枠は1日20回でした。** Gakkyが実際に使って確認した値です。
これは想定より二桁小さく、相談を数回した時点で上限に達します。しかも道具を呼ぶ
相談は往復が2回になるので、1回の相談で2回分を消費します。

サーバーの既定を `gemini-3.5-flash-lite` に変えました（`server/wrangler.jsonc`）。
**失うのは検算です。** 上の表のとおり Lite は方向は正しくても数字を確かめないので、
「10%下げるなら何個多く売る必要があるか」のような答えは弱くなります。
無料で毎日使えることを優先した、という判断です。

有料キーを常用するなら 3.6 に戻す価値があります。中間の `gemini-3.5-flash` は
まだ往復を測っていないので、無料枠と検算の両立が要るなら、ここを測るのが次の一手です。

**未検証の点。** 道具の呼び出しと JSON 出力の両立は `gemini-3.6-flash` で確かめた
もので、Flash-Lite では確かめていません。本番未公開の `search_memory` を出す前に、
このモデルで両立するかを必ず確認してください。

### 切り分けの手段

設定画面の「接続を確認」は、登録済みのキーで最小の呼び出しを1回行い、あわせて
**そのキーが使えるモデルの一覧**を取得します。モデルごとに「使える／使えない」が
出るので、応答しない原因がキーなのかモデルなのかを、相談を書く前に判別できます。

リクエストには45秒の時限を入れ、待機中は取り消せるようにしました。応答しない
モデルを選んだときに、何も出来ないまま待たされるのを避けるためです。

## 保存されるのは本文だけではない（修正）

`cached_messages` には本文と表情・ポーズ・シーンしか入れていませんでした。
選択肢、次の一手、判断、問い返しは、画面に出したあと捨てていたわけです。

影響は2つあり、後者のほうが重いものでした。書き出したログから選択肢が消える。
そして**アプリを開き直すと、過去のターンから選択肢も判断カードも消えます**。

`response_json` 列を足し、検証済みの応答をそのまま入れるようにしました。列を
フィールドごとに切らないのは、契約がまだ動くためです。読み戻すときは
`validateMayaResponse` を通します。古いビルドが書いた行が、いまは無い表情を
名乗っている可能性があるので、届いたときと同じ扉を通します。

列が無かった頃の行は本文だけで戻ります。書かれていないものは復元できません。

### Flash Lite と記憶の検索（2026-09-15 実測）

`gemini-3.5-flash-lite` に search_memory を渡し、架空の記録で3問を試しました。

| 質問 | 任せたとき | 過去を指す言葉で呼ばせたとき |
| --- | --- | --- |
| おはよう | 呼ばない（1.8秒） | 呼ばない（1.4秒） |
| 去年の春、値上げについて何か決めてたっけ？ | **呼ばず**「御社のことを何も聞いていない」 | 1回探して記録どおりに答えた（2.8秒） |
| 前に採用の件で何を決めたか覚えてる？ | **呼ばず**同上 | 1回探して「記録は無い」と答えた（2.6秒） |

- **Lite は、呼ぶかどうかを任せると呼ばない。** 3.6 Flash は自分で呼んだ。そこでサーバーが発言に
  「前に」「去年」「覚えて」などがあるかを見て、あれば最初の往復で呼ばせる（`refersToPast`）
- **呼ばせる指定（mode ANY）と JSON の指定は同時に使えない。** `INVALID_ARGUMENT` で拒否される。
  呼ばせる往復だけ JSON の指定を外し、答える往復で戻す
- 別の問題として、Lite は人物像の例文「さっき寝てないって言ってましたよね」を、言われていないのに
  使った。例文を字面どおり真似る傾向がある。プロンプト側で扱う
